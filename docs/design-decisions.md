# Как подтверждаются значения

| Правило | Зачем | Где закреплено |
|---|---|---|
| У значения есть точная цитата и позиции в карточке | Проверить источник заполнения | `domain/attribute_evidence.py`, unit-тесты |
| Числа и совместимые единицы нормализуются | Сопоставить значение со схемой категории | `domain/attribute_normalization.py`, unit-тесты |
| Противоречащие цитате значения исключаются до расчёта балла | Не заполнять поле ошибочным значением | `domain/evidence_validation.py`, unit- и интеграционные тесты |
| Балл подтверждения рассчитывается из признаков | Объяснить оценку конкретного значения | `domain/evidence_risk.py`, unit-тесты |
| Причины высокого балла показываются при выполненном условии | Объяснить точную цитату, значение, число и категорию | `domain/evidence_signals.py`, unit-тесты |
| Исправление связано с категорией и контекстом карточки | Не переносить правку на другой товар | `usecase/persistent_review.py`, интеграционные тесты |
| Пропущенное поле добавляется вручную с дословной цитатой | Сохранить проверяемый источник ручного решения без модельной уверенности | `usecase/review_addition.py`, интеграционные и браузерные тесты |
| Отклонение подавляет поле в обоих движках и не создаёт алиас | Не возвращать отвергнутое значение при повторном извлечении | `domain/review_decisions.py`, `usecase/flow_reviews.py`, `usecase/rule_reviews.py` |
| Решение и исправление записываются одной транзакцией | Не сохранять частичное действие | `repository/sqlite/uow.py`, интеграционные тесты |
| Исходная карточка, движок и выбранная категория сохраняются для очереди | Повторять исправленную карточку независимо от текущего ввода | `usecase/review_card.py`, `repository/sqlite/cards.py` |
| Новая категория сохраняется вместе со схемой | Повторно использовать найденные поля | `usecase/stand_attribute_flow.py`, интеграционные тесты |
| Оба движка и список категорий читают общий снимок схем | Использовать новую категорию и добавленные поля без перезапуска | `usecase/catalog_schemas.py`, `repository/memory/catalog_retrieval.py` |
| Профиль правил и кэш учитывают выбранную схему | Не смешивать одинаковые поля с разными единицами | `usecase/catalog_pack.py`, `usecase/extract_card.py`, интеграционные тесты |
| Тип сбоя шлюза сохраняется до API | Различать таймаут, перегрузку, недоступность и неверный ответ | `adapter/llm/gateway.py`, `usecase/flow_failures.py`, `controller/errors.py` |
| Ключ шлюза берётся из окружения | Не хранить секрет в исходниках | `settings.py` |

Пути в таблице указаны относительно `backend/src/app/`.
В запросе к шлюзу используется модель `default`; конкретная конфигурация
задаётся на стороне шлюза. Шлюзу передаётся строгая JSON-схема; приложение
проверяет структуру ответа, индексы полей и цитаты.

Черновик, последний результат и незавершённый запрос сохраняются в браузере.
Обновление страницы сверяет решения с сервером без вызова модели. Решение из
другой вкладки обновляет открытый результат. Незавершённое извлечение повторяется
только по явному действию; предыдущий результат доступен отдельно от черновика.

На стартовом экране показывается история извлечений. Каждый запрос сохраняется
в SQLite до обработки, затем получает статус и снимок ответа. После перезапуска
незавершённые запросы помечаются прерванными. При открытии завершённой записи
возвращаются исходный запрос и сохранённый результат без нового извлечения.
Снимок ответа сериализует контроллер; сценарий и репозиторий хранят его как JSON.
Правки доступны только внутри открытой карточки. Статус «Подтверждено» относится
к результату извлечения: внешняя запись товара в каталог не реализована.

Автоматическое принятие по порогу хранится отдельно как `auto_accepted`, без
`resolved_value` и без обучающего алиаса. Такие записи доступны для правки,
но не входят в очередь `pending`. Повторное извлечение пересматривает их
по текущему порогу; сохранённые решения человека не понижаются. Контракт,
настройки и локальное измерение группировки: [пакетная обработка](scaling.md).

Экспорт JSON использует тот же механизм сверки ручных решений, что и открытый
результат. Подготовка данных выполняется через TanStack Query в сущности карточки,
скачивание файла — в отдельной feature. Страница связывает её с результатом и
историей через слоты. Формат экспорта версионирован и сохраняет статусы пропусков
и проверки; при недоступном сервере экспорт не выдаёт устаревшее решение за свежее.

Проверка значения учитывает отрицания в окружающей фразе, числа и единицы,
сохранность диапазона, противоречащие друг другу именованные значения,
контекст упаковки и совместимого товара. Она применяется к полям категории
и дополнительным полям, повторяется после дополнения данными продавца.
Отвергнутое значение не попадает в ответ API и очередь подтверждения;
незаполненное поле категории остаётся в `missing`. Причина сохраняется в
`validation_errors` результата извлечения и в структурированном `rejections`
ответа API. Интерфейс показывает причину пропуска и цитату рядом с результатом.
Совместимые единицы и формы цвета
сопоставляются с нормализацией; исходная цитата и её позиции сохраняются.
Сохранённое исправление человека действует отдельно в контексте своей карточки.
Проверки разделены на связь цитаты с полем и товаром (`evidence_context.py`),
числа и диапазоны (`evidence_quantities.py`), отбор результата
(`evidence_validation.py`). Текстовые значения сопоставляются с сохранением
порядка слов и учётом форм слов. При повторении цитаты выбирается вхождение,
прошедшее проверку контекста. Косвенное подтверждение без совпадения значения
отклоняется. Правила не заменяют измерение качества на реальных карточках.

Контекст ограничивается отдельным утверждением: соседние отрицания и свойства
упаковки не переносятся на проверяемое поле. В обычном предложении число требует
названия поля или его алиаса. Для ссылки «у модели …» обозначение сверяется с
заголовком. Диапазон проверяется на порядок границ после перевода единиц.
Модели и артикулы сравниваются без изменения пробелов, дефисов и суффиксов.
Условная поддержка отклоняется: текущий формат значения не хранит условия.

Проверка отрицания выполняется до проверки точного обозначения модели: совпадение
`ABC` с цитатой из «Модель не ABC» не подтверждает значение. Учитываются и короткая
цитата, и окружающая фраза. Подпись другого поля из схемы категории запрещает
перенос его значения: «Цвет красный» не подтверждает бренд. Без явного названия
бренда цвет также не считается его подтверждением. При этом бренд и модель могут
извлекаться из названия товара без подписи поля. Расчёт балла повторяет ту же
проверку, чтобы прямой вызов оценщика не выдавал высокий балл отвергнутому значению.

Двоеточие связывает поле и значение только когда цитата захватывает его или
находится после него. Оно не переименовывает предшествующую цитату в заголовке.
При числовой проверке тире с пробелами после имени поля или его алиаса считается
разделителем; знак перед числом и минус после двоеточия сохраняются.
Обе причины ложного отказа найдены на val и закреплены отдельными регрессиями.
[Пересчёт сохранённых ответов и ограничения](benchmark.md#исправления-проверки-цитат-19-октября-2026-года).

[Формат причин отказа в API](api.md).

В отдельных командах `backend/benchmarks/` строки Arrow и JSON представлены
типом `Row = dict[str, Any]`: состав полей зависит от исходного датасета,
протокола и сохранённого ответа. Перед прогоном проверяются контрольные суммы
зафиксированных входов; извлечение выполняется через типизированные доменные
объекты и текущие usecase приложения.

В `backend/analysis/` неоднородные агрегаты Arrow/JSON также используют `Row`.
Такой же тип используется в командах dev-аудита, повторной обработки и разбора
ошибок `backend/benchmarks/`: они читают сохранённые версии протоколов и ответов.
Аудит разметки связывает решение с хешами входа и целевого gold; поддержка
требует точных цитат. Отсутствие найденной строки не становится меткой отсутствия
сведений. Историческая машинная разметка и проверка ассистентом сохраняют своё
происхождение и не переименовываются в независимую человеческую разметку.
Подготовка аудита поддерживает сохранённый API валидатора и его новую версию
с аргументом категории; повторный разбор использует текущий полный парсер.
Обёртка `NOTEBOOK_API: Any` ограничена API создания notebook в nbformat,
где функции библиотеки не снабжены типами. Окружение анализа устанавливается
отдельной группой `data` и не включается в production-образ.

Строки параметров продавца проверяются до отправки карточки. Пустые строки
допустимы; каждая непустая строка требует названия, двоеточия и значения.
Двоеточия внутри значения сохраняются. Ошибки показывают исходную строку,
её номер и способ исправления после выхода из поля или попытки отправки.
При ошибке запрос не запускается, раздел параметров раскрывается, фокус
возвращается в поле. Исправления обновляют список ошибок сразу; исходный
текст, включая ошибочные строки, сохраняется в черновике.

Валидатор допускает перестановку полного набора слов названия поля, сохраняя
все уточнения; направленные связки «на», «из», «от», «до», «to/from» остаются
зависимыми от порядка. Алиасы схемы дополняются названиями бренда/торговой марки.
Двоеточие внутри буквально найденного значения не становится новым полем,
если префикс не обозначает известное поле и справа не стоит флаг «Да/Нет».
Остальные проверки контекста сохраняются. Идентификаторы модели, серии и артикула
проверяются как точные строки: цифры и дефисы не превращают их в числовой диапазон.

Составное категориальное значение из флагов допускается, только когда каждая
часть входит в словарь поля и имеет отдельную положительную строку в исходной
цитате. Каждая строка повторно проходит обычную проверку контекста, отрицания
и конфликтов по полной карточке. Неизвестная часть, конфликт, пропущенная строка,
чужой объект или добавленная единица не подтверждают составной результат.
Баллы уверенности и операционный порог не становятся от этого калиброванной
вероятностью. Результат парного пересчёта и снижение precision сохранены
в [отчёте](../reports/validator-quality-v1.json).

Проверка автопринятия реализована отдельными ручными командами `benchmarks.acceptance_*`,
вне runtime. Исторические SKU, train и близкие словные триграммы исключаются до
извлечения. Настройки и разбиение фиксируются до рецензий. Два независимых
проверяющих видят полный вход и итоговые значения; выбранный пакет содержит
все автопринятые поля и контрольные ответы без баллов и статусов. Полные
поддержанные ответы остаются в знаменателе охвата. Рецензии привязаны к хешу
пакета, проверяются точные значения, категории и текст, а неизвестность и
разногласие считаются неподтверждением. Основная единица расчёта — карточка
со всеми автопринятыми полями; точная нижняя граница не учитывает ошибки
агентской разметки. Положительный результат не становится человеческой
калибровкой, отрицательный не скрывается. [Измерение](acceptance-validation.md).

Обычное предложение связывает поле с полным набором слов его названия, включая
перестановку и ограниченный набор служебных уточнений. Числительные словами
преобразуются в количество только рядом с названием считаемого объекта;
отрицания, приблизительность и условия не подтверждают точное число. Временной
показатель сохраняет режим использования и предел «до». Составная единица
не обрезается до её первой части. Точка внутри десятичного числа сохраняется,
а точка на конце цитаты завершает предложение.

Совместимость с ОС требует явного утверждения о совместимости или поддержки.
Неизвестность, условность, отрицание и название приложения вместо ОС отклоняются.
Список текстовых значений проверяется по отдельным дословным фрагментам полной
карточки; повторные компоненты и списки вместо булева значения не подтверждаются.
У новой категории имена отклонённых полей сохраняются в схеме без значения и
словаря, включая случай отказа по всем полям. Они остаются в списке пропусков.
Интерфейс учитывает отказы и отсутствие схемы при сообщении о заполненности;
ручное восстановление убирает устаревший отказ. Снимок истории сохраняет прежний
результат: повторная проверка новой версией требует явного извлечения.
