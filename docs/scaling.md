# Пакетная обработка и порог принятия

Карточки проходят дешёвую проверку правил до формирования групп для модели.
Полностью разобранные карточки не отправляются в модель; остальные объединяются
по числу карточек и фактическому размеру JSON. Схемы категорий и идентификаторы
полей общие для группы. Цитаты проверяются отдельно по тексту каждой карточки.

## Как объяснить масштабирование

«Для массовой загрузки мы используем пакетный API. Сначала правила обрабатывают
полностью структурированные карточки. Остальные идут в модель небольшими
группами с общей схемой. Число одновременных обращений и размер очереди ограничены,
поэтому большая загрузка не создаёт неограниченное число запросов. Результат
и ошибка связаны с ID карточки; повторить можно только неудавшиеся записи».

Группы уменьшают число обращений и повторение инструкций и схем. Параллелизм
позволяет выполнять несколько групп одновременно в пределах бюджета нагрузки.
Эти механизмы не заменяют измерение качества, токенов и скорости внешней модели.

## Проверенный локальный профиль

19.10.2026, 100 синтетических карточек, по два атрибута, `local_rules`, правила
маршрутизации выключены для сравнения группировки, лимит параллелизма 2:

| Режим | Обращения к адаптеру | Символы system + prompt + schema |
|---|---:|---:|
| По одной карточке | 100 | 275 090 |
| По четыре карточки | 25 | 80 540 |

Обращений на 75,00% меньше, передаваемого текста на 70,72% меньше. Результаты
двух режимов совпали, срезы цитат корректны. Это бесплатный профиль локального
алгоритма: он не измеряет токены, денежную экономию, качество LLM или пропускную
способность production. [Отчёт с параметрами и хешами](../reports/batch-local.json).

Повторить из `backend/` с новым выходным файлом:

```bash
uv run python -m benchmarks.batch_profile --cards 100 --batch-size 4 \
  --concurrency 2 --output ../reports/batch-local-repeat.json
```

Для N карточек, требующих модели, при одинаковом допустимом размере число
обращений составляет примерно `ceil(N / B)`, где B — размер группы. Ограничение
размера JSON может уменьшить B и увеличить число обращений. Качество группы
и долю ошибок нужно сравнивать на одинаковых карточках до увеличения B.

## API

`POST /api/v1/extract/batch` принимает от 1 до 100 карточек, суммарно до
240 000 символов исходных полей. Лимит отдельной карточки — 24 000 символов.
ID должны быть уникальны внутри запроса. Пакет использует `hybrid`; без ключа
этот путь выполняется локальным алгоритмом.

```json
{
  "items": [
    {
      "id": "seller-1:sku-101",
      "category_id": 761,
      "title": "Смартфон Север S1",
      "description": "Цвет: черный"
    },
    {
      "id": "seller-1:sku-102",
      "category_id": 761,
      "title": "Смартфон Север S2",
      "description": "Цвет: синий"
    }
  ]
}
```

В `items` ответа сохраняется порядок входа. Каждая запись содержит `id`,
`run_id`, `status`, `result` или безопасный `error`. Результат проходит те же
нормализацию, валидацию, порог и хранение правок, что и одиночное извлечение.
Каждая карточка сохраняется в обычной истории; `run_id` можно открыть через
`GET /api/v1/runs/{run_id}` без нового извлечения.

`summary` содержит число удач и ошибок, `provider_requests`, `provider_cards`,
`rules_only_cards`, `input_tokens`, `output_tokens`, `elapsed_ms` и `provider`.
`provider_requests` считает действительно начатые вызовы адаптера: в режиме
`local_rules` они не являются внешними вызовами LLM. Если провайдер не сообщил
токены, значения равны `null`, а не предполагаемому нулю.

Ошибка формата самого пакета возвращает HTTP 422 до извлечения. При частичном
сбое HTTP 200 содержит ошибки соответствующих записей. Некорректный JSON
ответа или сбой провайдера отклоняет затронутую группу; остальные группы
обрабатываются. Автоматических повторных платных вызовов нет. Для повтора
отправляются только записи со статусом `failed`.

## Ограничение нагрузки

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `EXTRACTION_BATCH_SIZE` | 4 | Максимум карточек в одном запросе модели, допустимо 1–16 |
| `EXTRACTION_CONCURRENCY` | 2 | Одновременные обращения в одном процессе, допустимо 1–8 |
| `EXTRACTION_MAX_BATCH_CHARS` | 48000 | Предел символов JSON prompt с карточками, схемами и подсказками |
| `EXTRACTION_MAX_PENDING` | 8 | Активные и ожидающие вызовы в одном процессе |
| `GATEWAY_TIMEOUT_S` | 120 | Таймаут группы, включая ожидание слота |
| `BATCH_PROXY_TIMEOUT_S` | 1800 | Ожидание ответа пакета через nginx, в секундах |
| `RULES_FIRST` | true | Пропуск модели для полностью разобранных карточек |

System и схема ответа не входят в `EXTRACTION_MAX_BATCH_CHARS`; их учитывает
локальный профиль текста запросов. Одиночная карточка вместе со схемами,
не помещающаяся в лимит prompt, получает `model_input_too_large`: текст
не обрезается. При заполненной очереди возвращается `model_capacity`,
при истечении общего таймаута — `model_timeout`, при отказе доменного парсера —
`invalid_model_output`. Сетевой таймаут также даёт `model_timeout`; недоступность
шлюза — `model_unavailable`, HTTP 429 провайдера — `model_rate_limited`,
повреждённый или обрезанный ответ — `invalid_model_output`. Неизвестный сбой
остаётся `model_failure`. [Статусы HTTP и поведение пакетов](api.md).

У пакетного endpoint отдельный таймаут nginx и ограничение тела запроса 4 MiB.
Для стандартных настроек 100 карточек требуют до 25 групп и 13 волн:
`13 × 120 = 1560` секунд ожидания модели без учёта подготовки и записи.
Поэтому общий таймаут одиночного извлечения 120 секунд для пакета не используется.
Если уменьшаете размер группы или параллелизм либо увеличиваете таймаут модели,
пересчитайте `ceil(ceil(N / B) / C) × timeout` и настройте nginx и HTTP-клиент
или уменьшите N. Разбиение по размеру JSON также увеличивает число волн.

Большой пакет обслуживается ограниченным числом задач. Отмена запроса освобождает
слоты; начатые записи истории получают завершённый или неудачный статус.
Это синхронный пакетный API одного backend с SQLite. Для нескольких процессов
и долгих фоновых заданий потребуются общая очередь задач и общее хранилище;
такой распределённый режим сейчас не реализован.

## Порог и защита

Перед расчётом балла проверяются точная цитата, поле, объект, отрицания,
противоречия, числа, единицы и диапазоны. Невалидное значение исключается
из заполненных полей и попадает в `rejections`; порог не может вернуть его обратно.
Путь новой категории проверяется до записи в SQLite.

Валидное значение автоматически принимается, только если одновременно:

- `risk.score >= ACCEPTANCE_THRESHOLD`, по умолчанию 0,95;
- риск низкий, нет предупреждений, категория известна;
- подтверждены точная цитата, связь значения с полем и наличие поля в категории.

Связь с полем, которую нужно проверить вручную, снижает эвристический балл
и объясняется причиной `field_unconfirmed`. Новые категории и дополнительные
поля проходят ручную проверку, даже если цитата точная.

| Исход | API | Хранение и действие |
|---|---|---|
| Значение отвергнуто | `rejections`, при необходимости `missing` | Не считается заполненным |
| Нужна проверка | `status=review`, `acceptance=review` | Очередь `pending` |
| Принято по порогу | `status=accepted`, `acceptance=automatic` | `auto_accepted`, доступно для правки |
| Решение человека | `status=accepted`, `acceptance=manual`, `source=review` | Решение и алиас записаны атомарно |

`confidence` содержит числовой балл подтверждения для автоматического результата,
`threshold` — настроенный порог, `auto_accept_enabled` — включено ли применение
порога. Этот балл является операционной эвристикой, а не откалиброванной
вероятностью правильности. `AUTO_ACCEPT=false` оставляет все новые значения
на проверке с сохранением баллов. Значение человека не получает выдуманную
вероятность; автоматическое принятие не создаёт обучающий алиас.

Порог 0,95 выбран как консервативная настройка, а не найден на test.
Для подбора рабочего порога нужны независимые размеченные val-карточки,
precision/coverage по порогам и проверка выбранного порога на отложенном test.
Обещание «95% правильных ответов» из числа 0,95 не следует.

Исторические F1 и стоимость другой конфигурации не становятся текущими
после изменения валидации. [Бенчмарк и его границы](benchmark.md).

## Измеренная проверка правила принятия

19.10.2026 [две независимые агентские рецензии](acceptance-validation.md)
не подтвердили цель95% для фиксированной политики0,95 на новом наборе.
Допустимые эвристические баллы равны1, поэтому повышение числового порога
не устраняет выявленные ошибки. Рабочая настройка не менялась; режим
`AUTO_ACCEPT=false` оставляет все значения для ручной проверки.
